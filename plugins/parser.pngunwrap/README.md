# PNG 壳分片剥离（parser.pngunwrap）

T3FAP 解析插件。把「伪装成 PNG 的 HLS 分片」剥回可播放的 TS，让飞牛影视 / Emby / Jellyfin
能正常播放 4k影视这类站点。

**不改动任何现有插件。** 它靠 `resource.priority = 8` 接管解析链，删掉就自动回落。

> **T3FAP 的优先级是「数值越小越优先」**，不是反的。官方插件的自述就是证据：
> `parser.default_vip` = 5「在解析链路中**优先执行**」→ `default_gateway` = 10「在 VIP
> 解析**之后**作为基础兜底」→ `3q/czzy/dushe` = 100/110/120「在默认解析**失败后**补充」。
> 所以本插件设 8：排在 VIP(5) 之后，但稳稳压在 gateway(10) 和 4k(25) 前面。

---

## 一、它解决什么问题

4kvms 一类站点的 HLS 分片不是裸 TS，而是在真正的 MPEG-TS 前面套了一段伪装成 PNG 的壳
（让 CDN、防盗链、`<img>` 预检以为是图片）。播放器看到 PNG 魔数直接放弃，表现就是
**一直转圈、只显示封面**。

本插件在自己的进程里起一个 HLS 反代：

```
播放器 → 平台代理 → 插件反代(127.0.0.1:18521) → 源站
                        ├─ /hls/<tok>.m3u8   改写分片地址
                        └─ /seg/<tok>/<n>    拉分片 → 剥 126 字节壳 → video/mp2t
```

平台的 `access_mode=proxy` 只做「带鉴权头转发」，字节透明，不会替你剥壳 —— 所以剥壳
必须由插件自己做。

**实测数据**：三个真实分片样本剥掉 **126 字节**后，长度都能被 188 整除，同步率 `1.0000`。

## 二、安装

### 先选包：源码版还是 pyc 版

每次构建都会出两个包，**内容完全一致**，区别只在有没有源码：

| 包名 | 里面是什么 | 什么时候用 |
|---|---|---|
| `parser.pngunwrap-0.4.6.zip` | `.py` 源码（含 `build.py`） | 要改代码、要调逻辑时用；也能直接装到平台 |
| `parser.pngunwrap-0.4.6.pyc.zip` | 只有 `.pyc`，无源码 | 日常使用、发给别人、不想暴露源码时装这个 |

两个包**用的是同一个插件 id，不能同时装**。换包或升级之前，先删掉旧的
`parser.pngunwrap/` 整个目录 —— `.py` 的导入优先级高于 `.pyc`，留着旧源码
新装的 pyc 就不会生效（0.4.5 起会在日志里警告）。

改代码的流程：解压源码包 → 改 `backend/*.py` → 在源码根目录跑
`python build.py`（要 CPython 3.11）→ 两个新包一起生成在上级 `dist/`。

### 放哪里

把 `parser.pngunwrap/` 整个目录放到 T3FAP 的插件目录下（与现有插件同级），例如：

```
plugins/market/parser.pngunwrap/
├── plugin.json
├── backend/
│   ├── __init__.pyc
│   ├── plugin.pyc
│   ├── pngu_unwrap.pyc
│   ├── pngu_proxy.pyc
│   ├── pngu_fetch.pyc
│   ├── pngu_hijack.pyc
│   ├── pngu_mount.pyc
│   ├── pngu_sign.pyc
│   ├── pngu_sign_worker.pyc
│   └── vendor/nbmovie_wasm_bg.wasm
└── tools/
    ├── rewrite_strm.pyc
    ├── trace_chain.pyc
    ├── mk_strm.pyc
    └── probe_stream.pyc
```

然后重启 T3FAP，在插件列表里应能看到「PNG 壳分片剥离」。

> **发布包里只有 `.pyc`，没有源码。** 这是 T3FAP 官方插件的同款做法 ——
> 官方 `parser.*` 插件的 `backend/` 里也是 `.pyc`。要点三条：
>
> - **必须编译成「和源码同目录、同名」的 `xxx.pyc`**（`compileall -b` 的布局），
>   **不能**放 `__pycache__/xxx.cpython-311.pyc` —— 后者只有配套 `.py` 存在时才会被用。
> - **必须用 CPython 3.11 编译**。pyc 是版本绑定的：官方插件包里的 magic 是
>   `0x0DA7`(3495) 就是 3.11。用 3.12/3.13 编出来的丢进容器会直接
>   `bad magic number`，插件加载失败。
> - **覆盖安装前先删掉旧插件目录**。Python 的导入优先级是 `.py` 高于 `.pyc`，
>   旧目录里如果还留着上一版的 `plugin.py`，新装的 pyc 等于没装。插件启动时会
>   在日志里警告「插件目录里还有旧版源码」，`health.details.shadow_sources`
>   非空就是这个问题。
>
> 自己从源码重建一遍：`python build.py`（在插件源码根目录），它会找 3.11、
> 编译、删源码、逐个校验 magic，再用 3.11 真 import 一次确认能加载。

> **为什么有 9 个 pyc，而官方插件只有 1 个？** 因为本插件是**多模块**结构：
> `plugin`（钩子与配置）、`pngu_hijack`（接管内核 302）、`pngu_mount`（挂到
> 平台应用）、`pngu_proxy`（内建 HLS 反代）、`pngu_fetch` / `pngu_sign`
> （取流与签名）、`pngu_unwrap`（剥壳算法），再加包标识 `__init__` 和一个
> **必须能独立执行**的 `pngu_sign_worker`（签名跑在子进程里，防崩主进程）。
> 官方那个插件把所有代码写在一个 `backend/plugin.py` 里，所以只有一个 pyc。
> 一个模块一个 pyc 是 Python 的正常形态，平台加载不关心文件个数。

> `vendor/nbmovie_wasm_bg.wasm` 是从 `parser.thirdparty.4k` 复制的一份**副本**，
> 不引用也不修改原插件文件。

## 三、三步验证（按顺序，别跳）

### 第 1 步：验链路（30 秒）

```json
{ "source_mode": "demo" }
```

播一次任意 4k 内容。这一模式返回内置写死清单，分片是合成的合法 TS 包 ——
**画面可能是黑的、播放器可能报没有视频轨，这都正常。**

判断标准只有一个：**清单和分片有没有被成功请求到**。

- 平台日志里能看到 `/hls/...m3u8` 和 `/seg/...` 的请求 → **127.0.0.1 链路通，方案成立**
- 报 502 / 超时 / SSRF 拦截 → 平台代理不放行内网，改走「第 4 节 B 方案」

也可以直接访问自检接口：

```
http://127.0.0.1:18521/__health
```

### 第 2 步：验剥壳（1 分钟）

```json
{ "source_mode": "manual", "external_m3u8": "https://你的源/a.m3u8" }
```

填一条已知是 PNG 壳分片的清单地址，播一次。这次应该有画面。
如果第 2 步能播、第 1 步不通，说明是平台代理的问题，不是插件的问题。

### 第 3 步：走自动

```json
{ "source_mode": "auto", "play_quality": "1080" }
```

插件从 `parse_request.meta` 里取 `data_id / secret_key / play_key`，
用 wasm 在**子进程**里签名，拿 `/video/play` 的 JSON，挑一个清晰度，交给反代。

## 四、配置

| 键 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | **软开关**。关掉立即完全让路给 4k 插件，不用卸载 |
| `supports_mode` | `4k` | `4k`=只接管 4k 来源；`any`=全接管，仅排查用 |
| `source_mode` | `auto` | `auto` / `manual` / `demo` |
| `external_m3u8` | 空 | `manual` 时用 |
| `base_url` | `https://www.4kvms.org` | 站点换域名改这里 |
| `play_quality` | `1080` | 取不到按 1080 → 720 回退 |
| `cookie` | 空 | 可选，登录态能拿更高画质 |
| `relay_mode` | `auto` | `auto`=只接管带壳的；`always`=裸 TS 也走 NAS 中转（见 6.5.2） |
| `access_mode` | `proxy` | `proxy`=平台在容器内代拉（推荐）；`direct`=播放器直连 |
| `bind_host` | `127.0.0.1` | 只影响插件内建服务；`direct` 才需要 `0.0.0.0` |
| `listen_port` | `18521` | 容器内部端口，和 8521 互不影响；被占用自动顺延 |
| `public_base` | 空 | 仅 `direct` 或走 DDNS/反代时指定；留空按请求 Host 生成 |
| `cache_mb` | `64` | 分片缓存字节上限 |
| `cache_ttl` | `30` | 播放后保留秒数 |

### 解析优先级到底是 8 还是 20？

这里有两个**完全不同**的东西，看混了永远对不上：

| | 谁的值 | 在哪改 | 生效时机 |
|---|---|---|---|
| `resource.priority` | 插件包里写的（本插件 = **8**） | 改 `plugin.json` 重新打包 | 安装时随包带进去 |
| 界面上的「解析优先级」 | 平台数据库里的那份（你截图里 = **20**） | 插件设置页 | 改完要**停用→启用**插件 |

**以界面显示为准**，不要以 `plugin.json` 为准。界面是平台真正拿去排序的值；包里写 8 只是
「期望值」，平台收不收、什么时候覆盖，不同版本不一样。你看到 20 说明它没采纳包的 8 ——
那实际生效的就是 20。

**但这不影响播放。** 两个理由：

1. 数值越小越靠前，**20 仍然小于 4k 插件的 25**，需要抢的时候照样抢在它前面。
2. 更关键：0.4.2 起接管的是内核 `/api/strm/o/<token>.m3u8` 的 302 路由，播 STRM
   **根本不走解析链**，`parse()` 一次都不会被调用。优先级只决定「平台主动去解析一条
   m3u8 时，第三方解析插件谁先试」—— 那是 `test-parse`、或者非 STRM 播放路径才会发生的事。

想确认优先级有没有下发到插件这一层，看 health（`/api/plugins/parser.pngunwrap` 或插件健康页）：

```json
"priority_in_manifest": 8,          // 包里写的
"priority_from_platform": null,     // 平台下发的（null = 它没往插件传）
"config_keys": ["enabled", "..."],  // 平台实际下发的所有键
```

`priority_from_platform` 是 0.4.9 加的。它非 null 说明平台确实把优先级塞进了插件配置；
是 null 说明那个数字只在平台自己手里，插件侧无论如何都看不到 —— 也就无从影响剥壳。

### 要不要额外开端口？（高频疑问）

**不需要。默认 `proxy` 模式下，对外永远只有 T3FAP 那一个端口（你这里是 8521 / 8525 反代），
其他平台的视频完全不受影响。**

原因：`18521` 是**容器内部的私有端口**，只有 T3FAP 自己的进程会去连它：

```
播放器 → https://blz.cc.cd:8525/api/strm/...   ← 对外唯一入口
              ↓（同一个容器内，Linux 回环）
         http://127.0.0.1:18521/hls/...         ← 插件私有，不出容器
```

所以：

| 场景 | `bind_host` | 是否要端口映射 | 对外端口变化 |
|---|---|---|---|
| `proxy`（默认，推荐） | `127.0.0.1` | **不要** | 无，仍是 8525 |
| `direct`（B 方案，备用） | `0.0.0.0` | 需要映射 18521 | 多一个端口 |

两点补充：

- `0.0.0.0` 并不是“换了个端口才能跑”，它只是**多监听一个网卡接口**，`127.0.0.1` 照样能访问。
  真正的区别是 `access_mode`：`proxy` 由平台进程代拉，`direct` 由播放器直连。
- 插件只接管 `4k` 来源（`supports()` 严格判定），其它平台的播放请求一律放行给原插件，
  不会因为装了这个插件而影响别处。

### B 方案：平台代理不放行内网时

只有当平台代理拒绝访问 `127.0.0.1`（SSRF 白名单）时才需要走这套。它会占一个额外端口，
而且**删插件后老 STRM 会 404，必须重建**。

```yaml
# compose.yaml
services:
  t3fap:
    ports:
      - "8521:8521"
      - "18521:18521"
```

配置改成：

```json
{ "access_mode": "direct", "bind_host": "0.0.0.0",
  "public_base": "http://你的NAS地址:18521" }
```

此时 STRM 里存的是插件地址，**卸载插件后需要重新生成 STRM**（见 5.3）。

## 五、卸载与回滚

### 5.1 不想用了，先关软开关

```json
{ "enabled": false }
```

`supports()` 第一行就返回 `False`，解析链立刻回落 4k。插件还在，但完全不参与。

### 5.2 真删

| 方式 | 效果 | 代价 |
|---|---|---|
| 平台界面停用 | 立即恢复 | 无 |
| 平台界面卸载 | 恢复 | 钩子里停服务、清缓存 |
| 直接删目录 | 恢复 | **需重启一次 T3FAP** |

第三种要重启，是因为内建 HTTP 服务跑在**平台进程内的线程**里（不是守护进程），
平台一重启就必然消失，不会留孤儿进程。

### 5.3 为什么删了不会破坏原有环境

1. 只读现有插件 —— wasm 用自己的副本，原文件时间戳都不变
2. 不碰数据库 —— 只有 `config_schema` 的值会留在平台 DB 里（几 KB 孤儿数据，无害）
3. `menus / settings_sections / task_templates` 全空 —— 界面零新增，删了没有空壳菜单
4. 优先级只在内存排序里生效 —— 删后自动回落 `4k(25)`
5. 缓存写在插件自己目录 —— 删目录即删缓存

**唯一要注意的**：`proxy` 模式下 STRM 存的是平台地址，删插件后平台会重新解析并回落 4k，
回到「能拉到清单但播不了」的原点；`direct` 模式下 STRM 存的是插件地址，删了会 404，
**必须重新生成 STRM**。所以推荐 `proxy`。

## 六、排障

### 6.1 先看「插件到底有没有被调用」

平台日志里搜 `PNGU-`。0.2.0 起每次 `supports()` / `parse()` 都会打一行：

```
[pngunwrap] INFO PNGU-supports 收到：{"url": "https://www.4kvms.org/play/xxx"}
[pngunwrap] INFO PNGU-parse  收到：{"target": {...}}
```

| 日志情况 | 含义 | 下一步 |
|---|---|---|
| 完全没有 `PNGU-` | 平台压根没问过本插件 | ①看优先级是否 8；②看播放走的路径是不是 `/api/strm/...` 的 302（见 6.2） |
| 有 `PNGU-supports` 但没有 `PNGU-parse` | 被问过，但 `supports()` 判了 False | 把「接管范围」改成「全部接管（排查用）」，确认是不是来源判定太严 |
| 有 `PNGU-parse` 但报错 | 取流失败 | 看报错文本；容器禁 JIT 就改 `source_mode=manual` |

内建服务上还有一份实时计数（平台代理有没有真的来拉流）：

```
curl http://127.0.0.1:18521/__diag
```

重点看 `counts`：`supports_calls` / `parse_calls` / `parse_ok` / `hit_hls` / `hit_seg`。
`hit_seg` 大于 0 就说明剥壳链路真的在跑了。

### 6.1.1 完全脱离平台自测（0.2.2 起）

内建服务上有个调试端点，可以直接用浏览器验证「拉清单 → 改地址 → 剥壳」：

```
http://<NAS地址>:18521/__test?url=<一条 PNG 壳分片的 m3u8>
```

返回里会给你 `playlist_url` 和 `first_segment_url`。依次打开：

- `playlist_url` → 分片地址应该已经变成 `/seg/<token>/<n>`（不再是 `.png`）
- `first_segment_url` → 应该返回二进制 TS，而不是 PNG

两个都对，说明剥壳本身没问题，剩下要查的就是「平台有没有把请求送到这里」。
（需要先把 `bind_host` 临时改成 `0.0.0.0` 才能从别的机器访问，验证完改回 `127.0.0.1`。）

### 6.2 `/api/strm/` 只返回 302，插件不生效（已实测确认）

飞牛影视播 STRM 时，请求的是 `http://<t3fap>/api/strm/o/<token>.m3u8`，平台直接回
**302** 跳到「生成 STRM 时存下的那个地址」。实测：

```
GET /api/strm/o/cJgiJC-iQ4dT.m3u8
302  Location: https://oss.douyinbit.com/m3u8/7383bebd….m3u8
Server: uvicorn
```

这个 302 是**内核**发的（`grep /api/strm` 在整个插件包里零命中），**不经过解析链**。
所以播放时日志只有 `HEAD/GET .../api/strm/... 302`，一条 `/hls/`、`/seg/` 都没有；
装不装、开不开本插件，现象完全一样。

**重新生成 STRM 也没用** —— STRM 里存的就是这条上游地址，302 只是把它念出来。

> **0.4.0 已经解决了这个死角**：插件把这条 302 路由本身包住了，`.strm` 不用改。
> 见 6.2.1。只有当接管没成功（平台版本差异）时才需要动 STRM 内容。

### 6.2.1 0.4.0 起：插件把这条 302 包住了（推荐，`.strm` 一个都不用改）

**这是 0.4.0 最重要的变化，也是前面「装了插件、还是 PNG」的最终解。**

插件和平台跑在同一个进程里，`app.router.routes` 里就躺着那条发 302 的路由对象，
它的 `.app` 是一个 ASGI 可调用对象。0.4.0 把它换成自己的包装器：

```
播放器 → /api/strm/o/<token>.m3u8
       → 包装器先调原 route.app，拿到 302 + Location
       → 探一下上游第一片（Range 只取前 256 KB）是不是 PNG 壳
           是 → 200 返回改写后的清单，分片指向 /api/strm/pngu/seg/<tok>/<n>
           否 → 把那个 302 原封不动重放回去
```

所以：

- **媒体库里已有的 `.strm` 完全不用改，也不用重扫。** STRM 里存的还是门票地址，
  被换掉的只是「内核里谁来响应这个请求」。
- **对非 PNG 来源完全透明。** 判定为不带壳时重放的就是原来那个 302，逐字节一致，
  连 `Location` 都不动。主清单（多码率 `#EXT-X-STREAM-INF`）也一律放行，不去猜。
- **探测失败也放行。** 超时、403、格式不认识 —— 统统回落到原 302，绝不阻断播放。
- 结论按上游地址缓存 30 分钟，同一部片子只探一次，不会每开一次都多等。
- 判定结果能随时看：`/api/strm/pngu/__hijack` 是接管状态，
  `/api/strm/pngu/__probe?url=<上游 m3u8>` 直接告诉你这个源「会不会被接管、为什么」。

日志里对应的两行：

```
接管 STRM 播放链路成功：已接管 2 条：/api/strm/o/{short_id}.m3u8, …
接管 STRM 流：https://oss.douyinbit.com/m3u8/….m3u8 → 分片改指向 /api/strm/pngu/seg/…
```

只接管 `/api/strm/` 下面以 `.m3u8` 结尾的路由，`/api/media/*` 和后台 API 一概不碰；
卸载时把原 `.app` 装回去。

> 前一条（6.2）说的「必须改 STRM 内容」是 0.3.x 的结论。0.4.0 改了做法：
> 接管内核路由，比改几千个文件省事得多。**下面 6.2.2 / 6.2.3 仍然保留** ——
> 平台版本差异导致接管失败、或者你想绕开平台直接播时，那两条路照样能用。

### 6.2.2 让 STRM 直接指向插件（不依赖平台解析链）

插件从 0.2.3 起支持「自包含入口」：把源地址 base64url 编进路径，不需要登记、
不需要数据库，重启即恢复。

**从 0.3.0 起推荐走 T3FAP 统一端口 8521**（插件会把自己挂到平台的 FastAPI 上，
播放器只碰 8521，不需要端口映射）：

```
http://<NAS>:8521/api/strm/pngu/hls/u/<base64url(原 STRM 内容)>.m3u8
```

生成这一行：

```bash
python tools/mk_strm.pyc "https://blz.cc.cd:8525/api/strm/o/cJgiJC-iQ4dT.m3u8" \
    --host 192.168.31.5 --platform
```

如果平台没给挂载机会（老版本 / 挂了别的东西），会回退到独立端口，这时改用：

```bash
python tools/mk_strm.pyc "<源地址>" --host 192.168.31.5
# → http://192.168.31.5:18521/hls/u/<b64>.m3u8
# 需要 bind_host=0.0.0.0 + compose 映射 18521
```

工具接受两种输入：

- **T3FAP 门票地址**（`/api/strm/o/…`）—— 推荐。门票 token 稳定，插件每次现跟
  302 去取当次的上游清单，上游地址换了也不用改 STRM。
- **上游 m3u8 直链** —— 会过期，每换一次就得改一次 STRM。

挂载是否成功，看平台日志里这一行：

```
挂到平台 8521 成功：已挂载到 core.xxx 的 /api/strm/pngu
```

或者插件自检里 `mount.mounted == true`。

### 6.2.3 批量改整个媒体库（片子多的时候用这个）

```bash
# 先预演：只列出会改哪些，不动文件
python tools/rewrite_strm.pyc --dir "D:/media/影视" --host 192.168.31.5

# 确认无误后写入（自动备份成 xxx.strm.bak）
python tools/rewrite_strm.pyc --dir "D:/media/影视" --host 192.168.31.5 --apply

# 想回滚
python tools/rewrite_strm.pyc --dir "D:/media/影视" --restore
```

只改「T3FAP 门票地址」和「上游 m3u8 直链」两种内容，已经是插件地址的自动跳过，
其它格式（本地路径、不是 URL）一律不碰。原文件是 UTF-8 无 BOM 就写回无 BOM，
原来有 BOM 就保留 —— 不会给文件偷偷加东西。

**改完必须在飞牛影视里重新扫描该媒体库**，否则播放的还是缓存的旧地址。

### 6.2.4 为什么挂在 `/api/strm/pngu` 而不是别的路径

平台播放器访问 `/api/strm/*` 时**不带任何 token**（`/api/strm/o/<token>` 是公开的），
说明这个前缀在鉴权中间件的白名单里。把插件路由挂在这个前缀下面，播放器才能直接
访问，不会被 401 拦掉。

挂载用的是 Starlette 标准 `app.mount()`，不依赖 FastAPI 版本；找不到主应用、挂载
抛异常、前缀冲突 —— 一律静默降级到独立端口，不会影响插件加载和平台启动。
`disable` / `uninstall` 时会原地把路由摘掉。

### 6.3 判断分片到底还是不是 PNG 壳

```
python tools/trace_chain.pyc "https://..../index.m3u8"
```

这个比 `probe_stream.py` 更全：它会跟 302、打印每一跳、再探分片。输出示例：

```
[1] /api/strm/o/xxx.m3u8
    状态: 302   → 302 去: /p/xxx.m3u8
[2] <终点>
    状态: 200   → 终点: 返回内容
终点是 m3u8：共 418 行，205 个分片
分片域名: file.icve.com.cn
判定: 分片直连上游（清单未改写）
PNG 魔数: 是   壳长: 61   同步率 剥后: 1.0000
结论: PNG 壳（壳长 61）→ 硬解会被壳卡住
```

**壳长不是固定的**，实测两派：

| 来源 | 壳头结构 | 壳长 |
|---|---|---|
| 4kvms 系 | 完整小 PNG（含 IEND），后接 TS | **126** |
| icve / douyinbit 系 | 8 签名 + 25 IHDR + 28 IDAT，**无 IEND** | **61** |

0.2.2 及以前用「剥完长度必须能被 188 整除」来判断，icve 系分片末尾有 12 字节残包，
永远不整除，于是被判定成「不是 TS」原样透传 —— **这就是“插件没把 png 剥成 ts”的真正原因**，
0.2.3 已改成按同步率判定（`body[::188]` 里 `0x47` 占比 ≥ 0.85）。

**「软解能播、硬解不能、还卡顿」就是有壳的典型表现**：FFmpeg 系软解会自己找 `0x47`
重新对齐，所以能凑合播；硬件解码管线要求字节严格对齐，直接拒绝并提示无法硬解；
落到软解后 CPU 跟不上，于是卡顿。

### 6.4 看一半关掉，过一会儿再看就「获取不到分片」（0.4.6 修）

这是**上游地址的时效**问题，不是剥壳出了错。两个叠加的原因：

| 原因 | 表现 | 0.4.6 的处理 |
|---|---|---|
| 会话 30 分钟闲置被回收 | 分片请求直接 404 `session gone` | 留「墓碑」（tok → 门票地址，24 小时），用门票重新走 302 拿新地址 |
| 复用了旧会话、清单没重拉 | 分片全 403/404 | 清单超过 20 秒就重拉；分片 401/403/404、越界、网络错误都会重建清单再试 |

关键点在「门票」：平台的 `/api/strm/o/<token>.m3u8` 每次请求都会 302 到**当次有效**的
上游清单，上游清单里的分片地址才是带签名时效的。所以只要记住门票地址，随时能把
整条链重新走一遍 —— 这也是为什么插件现在要把它存进会话和墓碑。

日志里会看到这些，说明自动修复生效了：

```
会话 s… 已被回收，按门票地址重建：https://…/api/strm/o/xxx.m3u8
分片 12 返回 403（上游地址过期），重建清单：https://…/000.png
分片 12 的上游地址已刷新
```

`/api/strm/pngu/__hijack` 的 `mem` 里新增 `tombs`，正常播放时是个位数到几十。

### 6.5 「浏览器能播，但电视盒子 / App 播不了」

**先别怀疑地址过期。** 这种情况九成是码流本身：4K 源的 HEVC、AC-3 音轨、
或者 TS 分片不规范 —— 浏览器的 MSE 软解能容错，电视盒子的硬解直接崩。
插件的剥壳只影响「分片开头那几十/上百字节」，跟编码无关。

一条命令看真相：

1. 在播放器里点一下播放（哪怕立刻报错）
2. 浏览器打开 `https://<你的地址>/api/strm/pngu/__inspect`

它会把**最近一次播放**的上游流摊开：清单前 1.2 KB、首片前 16 字节、
剥壳结果、TS 里的 PAT/PMT 和每个基本流的编码。重点看两处：

| 字段 | 含义 |
|---|---|
| `unwrap.shell` | `>0` 分片是 PNG 壳（该剥）；`=0` 是裸 TS，插件本来就不该介入 |
| `ts.streams[].codec` | `H.265/HEVC`、`AC-3` 这类电视盒子硬解不了 |
| `ts.sync` | 1.0 才是干净 TS；明显小于 1 说明分片有问题 |

判断顺序：

- `shell > 0` 且 `codec` 是 H.264 → 该剥没剥，回头查 6.2 接管有没有生效
- `shell = 0`、`codec` 是 `H.265/HEVC` 或 `AC-3` → **插件帮不上忙**，是源和
  播放端不匹配：换 H.264 的线路、或在播放器里关掉硬件解码
- `shell = 0`、`codec` 是 H.264、`sync` 也是 1.0 → 流没问题，去查播放端的网络
  （电视盒子常走 IPv6 或独立代理，出口 IP 和 NAS 不一致，而上游 m3u8 是按
  IP 发 token 的）

要指定具体地址也可以：把上游 m3u8（就是 `Location` 那一行）做 base64url，
拼成 `/api/strm/pngu/__inspect/<base64url>`。`/api/strm/pngu/__probe` 同样支持。

#### 6.5.1 实测一次带宽：`__speed`

码流没问题却还是卡，那就是线路。0.5.0 起带一个测速口 —— 它从**这台 NAS**拉
一个真实分片，算出「分片本身要多少码率」和「实际拉到多少」：

```
https://<你的地址>/api/strm/pngu/__speed
```

```json
{
  "seg": "https://cs.example.com/xxx/817200000.ts",
  "seg_bytes": 755948,
  "seg_sec": 6.65,
  "need_kbps": 550,          // 分片大小×8 ÷ #EXTINF 时长
  "got_kbps": 909,           // 实测
  "ratio": 1.65,
  "verdict": "勉强够（1.7 倍），网络一抖就卡；电视/App 缓冲小，多半就卡在这儿"
}
```

`ratio` 的判断标准：**≥3 倍**才算宽裕，1.3~3 倍是勉强，**<1.3 倍必卡**。

关键点：**播放器不是通过 NAS 拉分片的。** HLS 清单里如果写的是上游的绝对地址
（`https://cdn.../xxx.ts`），播放器会**直连那个 CDN**，NAS 上的测速只代表 NAS
这一侧的线路。两边都正常才能顺畅播放。

#### 6.5.2 让分片走 NAS 中转（`relay_mode=always`）

如果 `__speed` 显示 NAS 拉得动、但播放器那边卡，说明是**播放器到 CDN** 的
线路问题。这时把 `relay_mode` 改成 `always`：

| 值 | 行为 |
|---|---|
| `auto`（默认） | 只有分片真带 PNG 壳才接管。裸 TS 原样放行，播放器直连 CDN，NAS 不转流量 |
| `always` | **不管有没有壳**，清单里的分片地址全部改写成 `/api/strm/pngu/seg/…`，播放器只连 NAS |

`always` 的代价是所有分片流量都过这台机器（4K 一路几 Mbit/s），好处是播放端
只需要能连上 NAS —— 而 NAS 你已经在用它看别的片了，一定是通的。

改完不用重启平台，保存配置就会重挂（`set_runtime_config` 里会重跑一次挂载）。
`__hijack` 里的 `relay` 计数开始涨，就说明中转生效了。

### 6.6 诊断口自己打不开 / 转圈半天

**0.5.0 修。** 症状：打开 `/api/strm/pngu/__inspect` 要等二三十秒，最后
`TimeoutError: timed out`。

原因是诊断口拿「门票」地址去拉，而门票里的主机是**内网 IP**（实测
`http://192.168.31.5:8521/…` —— 飞牛影视跟平台在同一台机器，就用内网地址访问）。
插件与平台**同容器**，从容器访问这个内网 IP 会被 NAS 防火墙挡住，一直等到超时。
真正通的是 `127.0.0.1`：同一个监听端口，走回环。

现在按「回环门票 → 原门票 → 上次 302 目标」的顺序试，每档只给 6 秒，第一个
通的就用。返回里多两个字段：

| 字段 | 含义 |
|---|---|
| `src_used` | 实际成功用的是哪个地址 |
| `tried` | 每个候选的结果（`reached` + 错误信息） |

如果 `src_used` 是 `http://127.0.0.1:8521/…`，说明回环那条路是通的，
原门票不可达 —— 以后排障都以此为准。

**0.5.1 还补了两个相关的坑：**

- **`127.0.0.1` 和 `192.168.31.5` 同时超时** → 不是防火墙，是**自己请求自己**。
  `serve()` 原来是同步阻塞的，跑在事件循环里；它去拉门票时门票又打回自己，
  自己没空响应自己，于是两个候选一起 `TimeoutError`。现在 `serve()` 全部走
  `asyncio.to_thread`
- **播放器关了日志还在刷 `/api/strm/o/… 302`** → 自激环。门票指向平台自己，
  插件拉门票 → 又进中间件 → 再探测 → 再拉门票。现在出站请求都带
  `X-Pngu-Self: 1`，中间件认出就原样透传

### 6.7 唯独某一集播不了，前后几集都正常

先看 `__hijack` 的计数，分清到底是「有人在播」还是「自己诊断」：

| 字段 | 含义 |
|---|---|
| `hit` | 播放器真的来要流了 |
| `diag` | 有人打开 `__inspect` / `__probe` / `__speed` |
| `self_skip` | 插件自己拉门票绕回自己身上（已放行，不算播放） |
| `memo` | 上游清单 404，用留底顶上 |
| `pass` | 首片是裸 TS，原样放行 |

`hit` 不再掺诊断和自请求 —— 以前三者混在一起，数字一涨就误以为在播放。

**实测过的一类真因（0.5.1 起能自动救）：** 那一集的门票 `/api/strm/o/<token>.m3u8`
**稳定 302 到一个已经 404 的上游 m3u8**，连打十次都是同一个死地址；而清单里的
`.ts` 分片在 CDN 上照常 `206`。也就是说**清单地址过期了，分片还活着**。

0.5.1 每解出一份清单都会留底（**0.5.2 起按门票 token 存、保留 72 小时**），
上游一旦拉不到就还回去。判断有没有生效：`__hijack` 里 `memo` 开始涨，`last` 会写
「上游清单失效，用 N 分钟前的留底顶上」。

**为什么 0.5.1 按地址存不行、0.5.2 必须改成按 token：** 同一个门票在不同时间会
302 到不同的上游清单（实测同一集给过 `a54547a1` / `4169d05` / `c1f2406` 三个）。
「退出播放器再进来」会触发平台重新解析 → 换一个新地址 → 拿地址当键的留底
永远对不上。token 是门票里的那段（`/api/strm/o/<token>.m3u8`），不随解析变，
所以 0.5.2 用它当键。

如果 `memo` 一直不涨、而那一集还是打不开，就是**这个 token 从来没成功拿到过清单**
（比如刚加进媒体库就直接遇到上游故障）。这种只能等上游恢复，或者在源站上重新解析这一集。

### 6.7.1 退出播放器再打开同一个 STRM 就播不了（0.5.3 修）

这是 6.7 的**另一种形态**，症状很像但链路完全不同，容易混。

先问一句：平台的 `last_status` 是多少（`__hijack` 里能看到）？

| `last_status` | 含义 | 谁的问题 |
|---|---|---|
| `302` | 平台解析成功，跳到上游 | 上游清单/分片的问题 → 看 6.7 |
| `4xx` / `5xx` | **平台自己都没解析出来** | 解析插件的问题 → 本小节 |

`4xx/5xx` 这条路上，插件以前**什么都做不了** —— 包装器只认 301/302/303/307/308，
平台报错就原样透传，连日志都不留。

为什么平台会解析失败？看 4k 插件里这句：

```python
ACCESS_RESTRICTION_MARKERS = ('请先登录', '开通vip', 'vip会员', '会员权限', '访问令牌已过期')
```

上游 `play_key` 有寿命。**插件本身不缓存 m3u8 地址**，每次 `parse()` 都现场
wasm 签名 + 现场请求（反编译确认，见第八章）；所以失败不是「用了旧地址」，
而是「这次去要，上游不给」。

0.5.3 的做法：平台报错时先查留底，有就用（`rescue` +1），没有才原样发回（`err` +1）。

所以要让它能救你，前提是**这一集成功播过一次**（那时留底才建立）。

```bash
# 看有没有留底
curl -k "https://<你的域名>:8525/api/strm/pngu/__hijack" | grep -E "rescue|err|memo|last_status"
```

如果 `err` 在涨、`rescue` 一直是 0，说明这一集从来没成功播过，插件手里没原材料 ——
只能去 4k 站上重新解析这一集（或等它恢复）。

**顺便回答一个常见疑问：同一个 STRM 重复解析，是复用缓存地址还是每次重新拉？**

| 环节 | 行为 |
|---|---|
| 4k 插件 `parse()` | **每次重新签名 + 重新请求**，不缓存地址 |
| 4k 插件的 cookie | 缓存（`_auth_cookie` + `_auth_cookie_expires_at`），登录态才有 |
| 平台 `/api/strm/o/<token>.m3u8` | **每次请求都重新解析**（实测同一 token 不同时间跳不同地址）|
| 本插件的判定结果 | 缓存（`_VERDICT`），但只缓存「带不带壳」，不缓存地址 |

## 七、已知限制

- 默认只接管 4k 来源（`provider=4k` 或域名属于 4kvms 家族），其他来源一律放行
- 需要容器里有 `wasmtime`（4k 插件本来就依赖它）
- 4K 画质取决于源站是否给该片 2160 流
- 需要登录/会员的集，换令牌也救不回来，会返回明确错误
- 分片是「拉一片、剥一片、缓存一片」，不做整集预下载
- **已有 STRM 在 0.4.0 起不用改**：插件接管内核 302 路由，`.strm` 原样就能生效。
  只有接管失败（平台版本差异）时，才需要按 6.2.2 / 6.2.3 改内容或批量重写。

## 八、版本

**0.5.14** —— 平台把一张**已经失效**的上游地址一直念下去时，插件要自己发现并修好。

现场（2026-11-01，用户报「浏览器能播，飞牛播放器缓冲接不上、断断续续」）：

```
门票  GET /api/strm/o/2ZG_iu12Yt19.m3u8  → 302   40~86ms，连请求 6 次完全一样
302   → https://oss.douyinbit.com/m3u8/fa294fff….m3u8
上游  换 5 种 UA / Referer 全部 404「token 不存在或已过期」
日志  HEAD + GET 每 3 秒一对，`hit` 一直涨、`pass` 一直涨、`reparse` 始终 0
```

40~86 毫秒就返回 302，不可能是现场解析（4k 签名要几秒）。平台把上次的解析结果
记在 `drive-playback` 缓存里，**地址早就过期了它照念**；播放器拿到死清单 →
播不了 → 3 秒后重试 → 又是同一张死地址。重启 T3FAP 后第一次请求变成 **8.9 秒**、
目标换成新地址，立刻就好了 —— 根因确认。

插件为什么没兜住，两处都是自己的问题：

1. **成功结论缓存了 30 分钟**。第一次探活时地址是好的，之后地址过期，插件还拿旧
   结论一路 `pass` 放行。现在：结论只管「是不是壳」，**活不活**另有账 ——
   `LIVE_CHECK=25` 秒内验过就不重复验，超过就发一次 **HEAD**（几十毫秒、几乎
   不耗流量，比拉清单 + 32KB 分片便宜两个数量级）；只看 404/410 判死，
   **403 不判死**（防盗链的源对 HEAD 就是 403）。
2. **同一地址被反复要 = 播放器在重试**。`STRIKE_WINDOW=15` 秒内被要 3 次、
   且距上次强制验活超过 60 秒，就**不信缓存**，老实拉一遍。这条是给「VOD 一集
   只请求一两次清单、正常情况根本触不到」设计的兜底。

顺带修掉重解析那条路一直是死的：

- **门票写的是对外端口**（`blz.cc.cd:8525`），容器里平台监听的是 8521 ——
  按门票端口拼回环地址全是 `Connection refused`，「清平台缓存」「重走门票」
  两条内部通道全部走不通。现在先按提示端口 + `/proc/net/tcp` 捞候选，
  用 **0.4 秒 TCP 连接**筛出真正在 listen 的端口，再发一次 HTTP 探测确认，
  结果缓存 15 分钟（负结果只缓存 2 分钟）。
- **`/api/strm/cache/drive-playback` 不是免鉴权的**：外网一律
  `401 请先登录后继续`，伪造 `X-Forwarded-For` / `Host` 六种组合都没用。
  内部 HTTP 打不通时，退一步**在进程里直接调那条路由的 endpoint** ——
  鉴权是 `Depends`，直接调用根本不会求解（参数认不全就老实放弃，不瞎传）。
- `__hijack` 新增 `inner_base` / `inner_ports` / `repair`（上次重解析的
  status、有没有清成、失败原因）以及 `live` / `dead` 两个计数。
  「为什么没自动恢复」这一句，现在看一眼就有答案。

新增 `t_alive.py`（24 项）：缓存里是死地址但结论是成功、刚验活过不许重复 HEAD、
反复索取要强制验活、403 不许判死、对外端口 ≠ 内部端口、401 退进程内调用、
真活着时不许瞎折腾、端口候选排序与收敛。

**0.5.13** —— 解析和剥壳共用同一道**上游闸门**：一次失败之后，无论是平台重试、
官方插件兜底、还是我们自己的救场，**一个 4k 请求都不许再发出去**。

上一版（0.5.12）只挡住了「同一张门票的重复请求」。但解析失败还有另外几条放大路径：

| 放大路径 | 以前一次播放失败会发几次请求 |
|---|---|
| 平台重试 → 我们的 `parse` | 每次 1 次 |
| 我们失败 → 平台换官方 4k 插件 | 再 1 次 |
| 官方失败 → 我们的救场 `_rescue` | 再 1 次 |
| 救场里换画质 `quality / 1080 / 720` | 最多 3 次 |
| 官方选中直链 → 同源 HLS 线路枚举 | 再最多 3 次 |

也就是说最坏情况一次「播不了」能打出 **9 次**上游请求，而播放器每秒重试一次。
现在全部收进一个闸门：

- `pngu_fetch._GATE`：连续失败按 **20 / 60 / 180 / 600 秒**退避；403/429/5xx
  视为「上游在拒绝」，第一次就直接进长冷却（≥180 秒）；
- 关闸期间 `resolve_4k`、`_rescue`、`_try_hls_line`、以及**门票侧的重解析**
  全部直接放弃，连一个 socket 都不开；
- 「登录 / VIP / 令牌过期」**不冷却** —— 那不是限流，冷却只会让用户白等，
  而且换令牌就能好；这类失败也不再换画质重试（`play_key` 一样，换了白换）；
- 画质降级从 3 档收到 2 档（`MAX_TRIES`），同源线路枚举从 3 条收到 2 条；
- 解析缓存键补上 `play_key`。以前是 `(data_id, quality)`，换一集或换一次令牌
  都会命中**上一集**的地址，那个地址早已过期 → 播放失败 → 重试 → 又命中，
  形成「怎么都播不了」的死循环；
- 失败结果短缓存 30 秒（`NEG_TTL`）：10 秒内重试 8 次只发 1 次请求；
- 关闸时的 `parse` 返回 `retryable=false` + `non_retryable=true`，**明确告诉平台
  「别重试」**。

为什么官方 `parse` 也要管：它跟我们走同一个出口 IP。不管它，就是「我们这边停了，
它那边还在按播放器的节奏打」，封 IP 这件事根本拦不住。

诊断：`__hijack` 新增 `gate{open,left,fails,reason,blocked,hard,perm}` 与
`fourk.gated`、`repair_gated`。`gate.open=false` 就说明此刻一个 4k 请求都不会
发出去 —— 「解析总失败却一直在打源站」有没有被摁住，看这一个字段就够。

**0.5.12** —— 把「播放器重试」挡在平台解析之前：同一张门票 20 秒内重复请求，
直接回上次改写好的清单，**平台和 4k 源站一次都不碰**。

为什么必须做这件事：播放器打不开时的行为是**每秒重试一次门票**，而每一次重试
都会让平台重新解析一遍 —— 官方 4k 插件 `parse()` 是**现场签名**（wasm
`build()` + 一个上游接口请求）。一分钟几十次、一小时上千次，源站限流、封 IP
就是这么来的。

- `REUSE_WINDOW = 20`：窗口取 20 秒，足够盖住「连点几下 / 播放器快速重试」，
  又不至于把已经过期的分片地址反复喂给播放器；
- 只登记真正的平台门票（`/api/strm/o/<tok>.m3u8`），自包含的 `/hls/u/…`
  地址不登记 —— 那种地址最后一段常重名，登记进来会让不同源串台；
- 顺手把**已经拉到的清单正文**直接交给建会话，省掉一次上游拉取。对 4k 这类
  源这不是省流量：清单地址常带一次性签名，多拉一次就多一次被限流的机会。

诊断字段：`reuse`（复用次数 = 省下的平台解析次数）。它涨得越多，被源站限流的
概率越低。

**0.5.11** —— 官方 4k 解析选中**直链（mp4）**时，自动换到同源的 **HLS 线路**。

现场证据：门票 302 到 `.../FAMILYCLOUD/xx.mp4`（836 MB，`filename="嫁金镯.E20.mp4"`），
而同一个源的另一条线路是能播的 HLS。原因是官方 `parse()` 的算法：

```
parse() → _ordered_lines(meta) → 逐条 _resolve_stream() → 第一条成功就返回
```

线路表里混着云盘直链和 HLS。**直链排前面，后面那些能播的 HLS 就永远用不上**。
网页播放器那边用户看到的是 ts 分片（它走的是另一条线路），平台这边却 302 到一个
打不开的 mp4 —— 两边的观感差就是这么来的。

0.5.11 的做法是**借官方自己的签名实现**把其它线路试一遍（不自己发明协议）：
跳过它已选中的那条，逐条 `_resolve_stream()`，找到 m3u8 就换过去。

| 配置 | 默认 | 作用 |
|---|---|---|
| `fourk_integrate` | `true` | 包住官方 4k 插件（0.5.8 起） |
| `fourk_prefer_hls` | `true` | 官方选中直链时，改试同源 HLS 线路 |
| `fourk_substitute` | `false` | 真把地址换成我们的清单（**默认关**，见 0.5.9） |

换成 HLS 之后，照常探首片、带壳才接管 —— 直链被换掉不等于剥壳失效。

`__hijack` 新增字段：

| 字段 | 含义 |
|---|---|
| `fourk.direct` | 官方选中了直链（mp4）的次数 |
| `fourk.hls_switch` | 其中成功换到 HLS 线路的次数 |
| `fourk.hls_line` | 换到了哪条线路 |
| `fourk.hls_note` | 换线路这件事的说明（不会被后面的「裸流放行」覆盖） |

`last` 一行现在会把两件事串起来说，例如
`官方选中了直链（…E20.mp4），同源有 HLS 线路（line-2），已换过去；官方解析成功，首片是裸 TS，原样放行`
—— 以前只看后半句会以为插件什么都没干。

换不到 HLS 时**如实说明**：「同源没找到可用的 HLS 线路，原样返回」。这时能不能播
取决于源站防盗链，不是插件能解决的：实测那个天翼云 mp4 用 6 种 UA + 8 个 Referer
+ 完整 `Sec-Fetch-*` 全被 403（边缘层验签前就拒），属于账号态签名限制。

**0.5.10** —— 两个「静默放过」的坑。

1. **清单判定不能靠后缀**。`_looks_like_playlist()` 只认 `.m3u8`，而 4k 现场大量是
   签名地址（`lf26-imcloud-file-sign.bytetos.com/....?x-signature=...`），一个都不匹配。
   现场数据正是 `hit 22 = unheld 19 + err 3`，**一次判定都没发生**。改成
   `_sniff_playlist()`：2 KB Range 看开头是不是 `#EXTM3U`（容忍 BOM）。
2. **`fourk_substitute` 默认关**。0.5.8 的闸门只看「有没有配 `public_base`」，
   用户填了 `192.168.31.5:8521` 照样绕过 —— 那是宿主机 LAN IP，平台在容器里访问
   会被防火墙挡，解析直接 502。现在必须显式打开才替换地址。

顺带修掉熔断从不触发的 bug：`_failcool_left` 把 `until==0`（还在累计阶段）当成
过期 `pop` 掉，计数永远归零。播放器把平台锤了 209 次都没熔断就是这个原因。

**0.5.9** —— 「`hit` 涨、`pass`/`wrap` 全零」：**2xx 内联清单从来没被处置**。

平台解析成功后不一定发 302，它会**把清单正文直接内联返回**（200）。
而包装器原来只认 3xx，2xx 无条件透传 —— 请求确实进来了（`hit 209`），
一个判定都没做。现在 `cap()` 按三种形态分流：

| 形态 | 处理 |
|---|---|
| 3xx | 探 `Location`，死了就换/清缓存重解析 |
| 2xx | 看正文是不是清单，是就改写分片地址（`MAX_INLINE = 1MB` 泄洪） |
| 4xx/5xx | 扣住（平台自己解析失败**不发 302**，直接回错误码） |

**0.5.8** —— 把官方 `parser.thirdparty.4k` 包进来（`fourk_integrate`，默认开）。

不再「用我们自己的解析去替它」，而是**在它的结果上加一层**：

1. 它解析成功 → 探首片，带壳且能交出对外地址就换成我们的清单，裸流原样放行
2. 它解析失败 → 用**同一次调用里的 meta** 按我们的 cookie/画质重解一次，
   成功就按成功返回（否则平台直接 502）

只改 `streams[0].url`，其余字段一律不动；任何异常都原样交还。
装不上（类名/`plugin_id` 都找不到）就 `tick()` 里带 60 秒冷却重试。

⚠️ 当天这版**把平台打成了 502**：交出去的地址是探测到的 LAN IP + 8521，
容器访问宿主机 LAN IP 被防火墙挡，实测只有 `127.0.0.1:<同端口>` 通。
这就是 0.5.10 把 `fourk_substitute` 改成默认关的直接原因。

**0.5.7** —— 撤回 0.5.6 的 SPS 误判。**能解析出字段 ≠ 解析对了。**

用户贴的 `__inspect` 说 `sps_total=2, sps_invalid=1`，0.5.6 据此把一组 SPS 改成了
filler（`0x67 → 0x0C`）。拿真实样本复算后发现：**两组 SPS 字节完全相同**，都是
1920×1080、`sps_id=0` —— 编码器每个 IDR 前重发参数集，完全正常。

错在扫描方式：在**整段 TS 字节**上 `find(b"\x00\x00\x01\x67")`，SPS 跨包时
4 字节包头 `47 xx xx xx` 被算进 NAL，于是拿到 32 字节而不是 28 字节，
exp-golomb 一错位就解出 `1666×-280`。

正解是分层：

```
TS → PAT → PMT → 视频 PID → 拼 PES 成 ES → 只在 ES 里找起始码 → 映射回文件偏移
```

`_raw_nals` 只兜底，且必须 `trusted=False`，**不可据此改字节**。
改码流还加了安全闸：同 `sps_id` 有合法 SPS 顶替、或没有 PPS 引用它，才允许动手；
拿不到 PMT 一律不动。`sps_fix` 默认由 `first` 改为 `off`。

**0.5.6** —— 找到并修掉「硬解失败、软解能播」的一个真实成因：**畸形 SPS**。

用户的 `__inspect` 报出 `1666x-280`。追下去发现首片里**有两组 SPS/PPS**：

| | `pic_height_in_map_units_minus1` | `frame_mbs_only_flag` | 算出的尺寸 |
|---|---|---|---|
| 第 1 组 | 1 | **0**（隔行） | 1920×64，再裁掉 344 行 → **1920×-280** |
| 第 2 组 | 67 | 1（逐行） | **1920×1080** ✓ |

物理上不存在的画面。硬解器按第一组初始化 surface 会失败，FFmpeg 软解会跳过
坏参数集继续找 —— 这就是「硬解必挂、软解能播、快进到后面又好了」的完整成因
（后续分片里没有这组坏 SPS，我抽查了 5 个分片确认）。

而 `_video_params` 原来「拿到第一个 SPS 就收工」，正好拿的是坏的那个。

**两处修复：**

1. **诊断不再被带偏**：`_h264_sps` 增加合理性校验（尺寸必须为正、偶数、
   ≤8192×4320），`_video_params` 收集全部 SPS 后挑合法那组，并报出
   `sps_total` / `sps_invalid`。结论里会写「同片里另有 N 组非法 SPS，
   硬解器可能先被它带偏」。
2. **新增 `sps_fix` 配置**，把坏 SPS 就地废掉：只改 **1 个字节**，把 SPS 的
   NAL header `0x67` 换成 filler data `0x0C`。长度不变 → 不用重打包 TS、
   不用改 `PES_packet_length`、不用动连续计数器。改之前必须真的解析出
   「不合理」，解析失败一律不动。

`sps_fix` 三档（**0.5.7 起默认 `off`**，原因见下面 0.5.7 那条）：

| 值 | 行为 | NAS 经手的流量 |
|---|---|---|
| `off`（默认） | 完全不碰码流，只在诊断里报出可疑参数集 | 0 |
| `first` | 只把**首片**指向本服务，其余分片仍由播放器直连 CDN | 一集 200 MB → 1~2 MB |
| `all` | 所有分片都过 NAS 再修 | 全过 |

`t_sps.py`（44 项）验证：诊断挑出合法组、修复只动 1 字节、同步率仍 1.0、
TS 包数不变、**正常分片字节完全不变**（宁可放过不能改坏）、幂等。
其中第 10 组用真实 HTTP + Range 跑通了 `_probe` 的识别路径。

**0.5.5** —— 把探测的取字节数从 256 KB 降到 32 KB，**起播快 5~8 倍**。

判定到底需要多少，两个常量说了算：

```
SEARCH_WINDOW = 1024          壳长搜索窗口，1 KB 就够
_ts_sync_rate 采 100 点 × 188 字节 ≈ 18.8 KB
```

合计 20 KB 上下。而原来写 262144，在实测 100~200 KB/s 的源上，**光这一次
Range 请求就要 1.3~2.6 秒**，播放器每打开一次都要等它 —— 这就是「反应慢」
的直接来源。降到 32 KB 后同样线路只要 0.2~0.3 秒。

`t_pbytes.py`（36 项）证明了判定结论与整片完全一致：裸 TS、126/61/73/120
四种已知壳长、137/200/512 三种表外壳长，以及真 PNG 和随机字节不误判。

顺带把 `120` 补进 `SHELL_SIZES`（xhscdn 系实测壳长），省掉一次窗口扫描。

**0.5.4** —— 让「每次打开都拿到最新地址」真的成立。

用户的 `__hijack` 长这样：

```json
"last_status": 302,
"last": "放行 https://oss.douyinbit.com/m3u8/9fb84de3….m3u8（清单拉取失败：404）",
"memo": 0, "pass": 13
```

平台**解析成功了**（302 拿到了地址），但那个地址 404；插件判定「死了」之后
只是**把死地址原样放行**——播放器当然打不开。`memo` 是 0，因为这一集从来没
成功拉到过清单，也就没留底可顶。

**「能不能每次打开都重新拿最新地址？」能，但不能由插件自己去 4k 拿。**
4k 插件 `parse()` 要 `data_id / secret_key / play_key`，这三样是平台在生成
STRM 时存在它自己库里的，插件侧拿不到。**但平台本来每次请求门票都会重新
解析**——只要它的缓存不挡路。

挡路的就是它自己：`/api/strm/cache/drive-playback` 记着「这个 STRM 上次解析
到哪儿」，地址死了它照样念。所以 0.5.4 的做法是：

```
播放请求 → 平台 302 到 X → 探测 X 死了
        → DELETE /api/strm/cache/drive-playback   （清平台缓存）
        → 重走一次门票 → 平台这次真的重新解析 → 拿到 Y
        → 探测 Y 可用 → 302 到 Y
```

- 新配置项 **`auto_reparse`**（默认开），关掉就只走留底兜底，不碰平台缓存
- **10 秒冷却**：HLS 播放中播放器每 4~10 秒重拉一次清单，那是「播放中」不该
  重新解析；而「退出再打开」必然超过 10 秒。10 秒正好把两件事分开
- **失败结论只缓存 30 秒**（以前 30 分钟）。踩过的坑：上游刚 404 那一下被判
  死，结论一存半小时，期间恢复了也不会再探
- 新诊断口 **`/api/strm/pngu/__cache`** 看平台缓存统计，
  **`/api/strm/pngu/__cache/clear`** 一键清空
- `__hijack` 新增 `reparse` / `reparse_ok` / `cache_clear` 三个计数

**0.5.3** —— 修「退出播放器、过一会儿再打开同一个 STRM 就播不了」。

先说清 4k 插件的解析逻辑（反编译 `parser.thirdparty.4k 0.1.0` 确认，magic 3495 = CPython 3.11）：

```
parse() → _ordered_lines() → _resolve_stream()
    wasm build(data_id, secret_key, quality, play_key)   ← 现场签名
    → urljoin(host, "/video/play?...") → urlopen        ← 现场请求
    → parse_play_response() → m3u8 地址
```

**它不缓存任何 m3u8 地址**，每次 parse 都重新签名、重新请求。模块级只有 `time`
（登录签名的 nonce/时间戳），没有缓存字典。唯一被缓存的是 **cookie**
（`_auth_cookie` + `_auth_cookie_expires_at`）。

所以「重复解析拿到旧地址」不成立。真正的情况是反过来：**上游会拒绝**。插件里写着

```python
ACCESS_RESTRICTION_MARKERS = ('请先登录', '开通vip', 'vip会员', '会员权限', '访问令牌已过期')
```

`play_key` 一过期，`parse()` 就抛错，平台于是**连 302 都不发**，直接回 4xx。

而 0.5.2 及以前的包装器只认 301/302/303/307/308：

```python
if code in REDIRECT_CODES and _looks_like_playlist(loc):
```

平台报错时这条不成立 → 原样透传 → 播放器永远打不开，**留底明明存着却一次也用不上**。

0.5.3 把 4xx/5xx 也扣下来：

- 平台解析失败 → 先查留底，有就用（`rescue` 计数 +1），没有才原样发回错误（`err` +1）
- `__hijack` 新增 `last_status`：平台内核这次对门票到底回了 302 还是 404，一眼可见
- 留底只收**裸流**（`wrapped = False`）：带壳源顶上后分片还是 PNG 壳，照样播不了，
  不给假希望

配合 0.5.2 的「按门票 token 存」，整条链才闭环：**成功播过一次 → 留底 → 之后
平台解析失败也能播。**

**0.5.2** —— 修 0.5.1 留底**命不中**的问题。0.5.1 是按上游地址存留底的，
但同一个门票不同时间会 302 到**不同**的上游清单（实测 `a54547a1` → `4169d05`
→ `c1f2406`），地址一换就再也对不上 —— 而「退出播放器再进来」恰好会触发重新
解析、换一个新地址，于是留底形同虚设。

- 留底改按**门票 token**存（`/api/strm/o/<token>.m3u8` 里的 token，稳定不随解析变）
- 保留期从 12 小时提到 **72 小时**（今天看两集、明天接着看是常态），上限 600 条
- 新增测试用例复现这条路径：换上游地址后仍要命中留底

**0.5.1** —— 修 0.5.0 自己捅出来的两个洞，外加一个真正解决「唯独某一集播不了」的功能。

- **诊断口不再拖死平台。** `serve()` 是同步阻塞的（要拉清单/分片），原来直接在
  事件循环里跑 —— 它去请求自己的门票时，自己没法响应自己，**127.0.0.1 和
  192.168.31.5 一起超时**（用户截图里两个候选都 `TimeoutError`，正是这个特征）。
  现在全部走 `asyncio.to_thread`
- **断掉自激。** 门票指的其实就是平台自己，插件拿门票去拉清单会绕回同一个中间件，
  再探测、再拉门票 …… 日志里 `HEAD/GET /api/strm/o/… 302` 刷屏、播放器早关了还在
  跑，就是这个环。`pngu_fetch` 现在给每个出站请求盖 `X-Pngu-Self: 1`，中间件见到就
  **原样透传**，一个字节都不碰
- **计数分开，别再误导。** `__hijack` 里拆成 `hit`（真实播放）/ `diag`（诊断口）/
  `self_skip`（自己的回环请求）/ `memo`，另附 `counters` 中文说明。以前三者混在
  `hit` 里，看到数字在涨很容易误判成「有人在播放」
- **上游清单 404 时用留底顶上。** 实测：同一部剧前后两集正常，中间那集的门票
  **稳定 302 到一个已经 404 的上游 m3u8**，而那批 `.ts` 分片在 CDN 上照常 206 ——
  清单地址过期了，分片还活着。现在每解出一份清单就留个底（12 小时 / 最多 400 条），
  上游一旦拉不到，把上次那份原样还回去，这一集就不会整个打不开

**0.5.0** —— 针对「浏览器能播、App / 电视播不了，而且反应特别慢」的四件事。

- **诊断口不再干等 25 秒。** 门票里的主机是内网 IP（`192.168.31.5:8521`），
  插件在容器里访问它会超时（防火墙不放行容器网段）。现在按「回环门票 →
  原门票 → 上次 302 目标」逐档试，每档 6 秒，第一个通的就用；返回里给出
  `src_used` 和 `tried`，一眼看出哪条路走得通
- **新增 `/api/strm/pngu/__speed`**：从 NAS 实测拉一个真实分片，算出
  `need_kbps`（分片码率）、`got_kbps`（实测带宽）、`ratio` 和结论。判断
  「是流的问题还是线路的问题」不用再猜
- **新增 `relay_mode` 配置**：`auto`（默认，只接管带壳的）/ `always`
  （裸 TS 也强制走 NAS 中转）。用在播放器到上游 CDN 线路太差、但 NAS 拉得动
  的场合 —— 播放端只需要能连上 NAS
- `state()` 增加 `relay_mode` 与 `relay` 计数；`configure()` 多一个
  `relay_mode` 参数，非法值忽略

**0.4.9** —— 把「解析优先级」这件事**做成可核对的**。起因是平台上插件设置页显示
「解析优先级 20」，而包里写的是 `resource.priority = 8`，两个数对不上，无法判断哪个
在生效。新增三个 health 字段（见第四章「解析优先级到底是 8 还是 20？」）：

- `priority_in_manifest`：包里写死的值（8）
- `priority_from_platform`：平台通过 `set_runtime_config` 下发下来的、列表里任何
  名字带 `prior` 的键。**null 就说明平台没往插件这层传**，那这个数字只在平台内部
  排序用，插件侧看不到也无从影响
- `config_keys`：平台实际下发的**全部键名**（含 `config_schema` 之外的），用来区分
  「平台没传」和「传了但被我们丢了」

`set_runtime_config` 不再把未知键默默扔掉，而是留档。功能行为没有任何变化 ——
优先级本来就不参与剥壳决策（播 STRM 走的是接管 302 那条路，不经过解析链）。

**0.4.8** —— 修 `__inspect` 的**误报**。它原来拿「上一次播放时的 302 目标」去拉，
而上游地址的时效只有几分钟（实测同一个门票，15 分钟前给的是 A 地址、现在给的是
B 地址），所以诊断结果经常是 `404 Not Found`，看起来特别像「地址过期」。

- 无参模式改成用**门票**（`/api/strm/o/…`）去拉：平台会把它重新解析成当前有效
  的上游地址，诊断永远拿到新鲜的
- 返回里 `src` 是门票、`final` 是解析后的真实上游地址、`note` 写明「已通过门票
  重新解析」；另附 `last_loc` 与 `last_loc_age_sec`（上次 302 目标及其年龄）留底
- `_LAST` 从单值改成 `{entry, loc, ts}`，`state()` 同时给出 `last_loc` / `last_entry`

**0.4.7** —— 新增**码流体检** `/api/strm/pngu/__inspect`。起因是「同一个链接浏览器
能播、飞牛 App 和电视播不了，报 `-875574520`」——这类问题跟剥壳无关，得看码流
本身是什么编码。

- `__inspect` 把最近一次播放的上游流摊开：清单前 1.2 KB、首片前 16 字节、
  `unwrap` 结果（壳长 / kind）、以及 TS 结构分析
- 自带一个轻量 TS 解析器：走 PAT → PMT，把每个基本流的 `stream_type` 翻成
  人话（`0x1B`→H.264、`0x24`→H.265/HEVC、`0x81`→AC-3、`0x87`→E-AC-3 …），
  同时给同步率。**不依赖 ffprobe**，容器里没装也能用
- 诊断口参数改走 path：`/__inspect/<base64url>`。挂载模式下 ASGI 拿到的是
  纯 path，`?url=` 那种 query 会被吃掉，之前 `/__probe?url=…` 在真机上一直
  报「参数为空」就是这原因
- 不带参数时分析**最近一次播放请求**（`state()["last_loc"]`），播一下再打开
  就能看，不用自己拼 base64

**0.4.6** —— **修「看一半关掉、过一会儿再看获取不到分片」**。用户实测：第一集播到
一半关掉，隔一段时间回来整集播不动。不是剥壳的问题，是**上游分片地址的时效** +
**会话生命周期**这两层叠加：

- **会话超过 20 秒就重拉清单**（`SESS_REFRESH`）。之前复用会话是「只要 tok 一样就
  直接吐上次那份 playlist」，播放器关掉再打开时拿到的还是上一次那批过期地址，
  一片都取不到。现在超过 20 秒就重新走一遍，续播一定拿新的
- **会话被回收后能自己回来**：`_TOMB` 记住 `tok → 门票地址`（`/api/strm/o/…`），
  留 24 小时。播放器手里那张旧清单里的分片路径是 `seg/<tok>/<n>`，只要它还来要
  分片，插件就用门票重新走一遍 302 拿新上游地址，会话原地重建
- **分片取流兜底链**：401/403/404、越界、网络错误，都先重建清单再试一次；重建
  优先用门票地址（上游 m3u8 自己过期时唯一能救回来的入口），失败再退回上游地址
- `state()["mem"]` 新增 `tombs`；清扫线程按 `TOMB_TTL` 清过期墓碑，不会无限留

**0.4.5** —— 新增**旧版源码残留检测**。Python 的导入优先级是 `.py` 高于 `.pyc`，
所以「覆盖安装」（旧目录没删、新包解压在上面）时，上一版的 `plugin.py` 会被优先
导入，**新装的 pyc 等于没装** —— 症状和「插件根本没生效」完全一样，且极难自查。

- 插件启动时扫一遍自己所在目录，发现 `.py` 就 warning：
  「插件目录里还有旧版源码（…）—— Python 会优先用 .py，新装的 .pyc 不会生效。
  请删除整份旧插件目录后重新安装」
- 同一份清单也放进 `health.details.shadow_sources`，远程排障直接看这个字段
  （空列表 = 正常）
- 源码版本不受影响：自己就是 `.py` 时不做这个检查

**0.4.4** —— **发布包只放 `.pyc`，不再随包带源码。** 功能与 0.4.3 完全一致，
只多了三处「没有源码也要能正常跑」的适配：

- `pngu_fetch.worker_script()`：签名子进程原来写死 `pngu_sign_worker.py`，
  现在按 `.py` → `.pyc` 顺序找第一个存在的，发布包里自动用 `.pyc`
  （CPython 支持直接执行 pyc）
- `plugin._disk_version()` 会从**字节码**里读 `__version__`：升级自检原来按行读
  `.py`，pyc 包里读不到就永远判「版本一致」，旧模块赖在内存里不换 ——
  那正是 0.4.0 那个 `TypeError: unexpected keyword argument` 的源头。
  配套的 `_module_file()` 会顺着改后缀、查 `__pycache__` 找真实文件，再从
  `co_consts` 里取形如 `1.2.3` 的常量
- 编译固定用 **CPython 3.11**（与容器一致），打包时逐个校验 magic = 3495，
  最后用 3.11 真 `import` 一次确认能加载

> 为什么不能用开发机的 3.13 编：pyc 与解释器版本强绑定。3.13 的 magic 是
> `0x0DF3`，容器里直接 `bad magic number`。判据来自官方插件包 ——
> 里面 pyc 的 magic 是 `0x0DA7`(3495)，也就是 3.11。

**0.4.3** —— **补上内存回收**。之前三张缓存表（分片 / 会话 / 判定）只有「写入时
顺便淘汰」，播放器关掉后不会再有写入，过期分片就一直躺在内存里 —— 播几部片子能
攒到接近 96 MB 不动，在 4 GB 的 NAS 上还要跟转码抢内存。

- **后台清扫线程**：每 30 秒扫一次，只清已过期的分片、闲置 ≥30 分钟的会话、
  过期的探测结论；三张表都空了就自己退出，不留常驻线程。用 `Event.wait` 而不是
  `sleep`，停用插件时能被立刻叫醒退出
- **停用即释放**：`release()` 立刻清空三张表，插件 `_shutdown` / `unhijack` 都会调
- **上限跟配置走**：接管链路的分片缓存现在读界面上的「分片缓存上限 / 保留秒数」，
  不再写死 96 MB / 60 秒（`configure()`）
- **计数改增量维护**：内建服务的 `SegmentCache.put` 原来每次都 `sum()` 全表，
  几千个分片时纯浪费 CPU；现在维护 `bytes` 计数器，`stats()` 顺手给出 `max_mb`
- **诊断可见**：`/api/strm/pngu/__hijack` 的 `mem` 字段给出
  `segments / sessions / cache_mb / cache_max_mb / seg_ttl / reaper`

**0.4.2** —— **修「挂载成功、接管却说没有匹配到 STRM 播放路由」**。真机日志：

```
INFO 挂到平台 8521 成功：已挂载在 /api/strm/pngu
INFO 接管 STRM 播放链路未成功：没有匹配到 STRM 播放路由
```

挂载成、接管败，说明「找到的 app」和「真正在播的 app」不是同一层。0.4.1 只认
`mod.app` 且只看主 app 的 `router.routes` 顶层，平台一旦把路由放进子应用、
把 app 挂在别的属性名或容器里，就一条都匹配不到。

- **应用发现放宽**：扫所有模块的所有属性（`app` / `application` / dict / list），
  都没有时用 `gc` 兜底按类名找存活对象
- **按路由归属反查**：谁的路由表里有 `/api/strm/*.m3u8`（含 `Mount("/api", 子应用)`
  这种嵌套，路径按前缀拼全），就挂谁、接管谁；归属统一取**根应用**
- **挂载插到路由表最前面**：平台若 `app.mount("/api", 子应用)`，排在它后面会
  被抢先匹配成 404
- **`/api/strm/pngu/__dump`**：直接列出「找到几个应用、各自有没有 strm 路由」，
  无需再猜

**0.4.1** —— **修「装上了但 302 照旧」**。真机日志给出铁证：

```
WARNING 启动时初始化未完成：TypeError: HlsProxy.__init__()
        got an unexpected keyword argument 'public_base'
INFO enable
GET /api/strm/o/ngWGBpNGEnJ_.m3u8 302      ← 接管根本没装上
```

根因不是参数写错，是**平台热更新只重新导入 `plugin` 模块**，`pngu_proxy` 还赖在
`sys.modules` 里 —— 新版 plugin 去调旧版类，构造就炸，挂载与接管跟着一起废掉。
而且 `enable()` 里没有重跑初始化，用户点「重新启用」也救不回来。

三处修复：

1. **每个后端模块末尾加 `__version__`**，`plugin` 启动时比对「内存 vs 磁盘」，
   不一致就先把旧现场拆干净（卸路由 / 摘挂载 / 停实例）再 `importlib.reload`
   子模块。`health` 的 `details.modules` 里能直接看到版本对不对。
2. **`enable()` 也跑一遍初始化**（`force=True`，不受 15 秒重试间隔限制）——
   用户点启用就是在催，等 15 秒等于又白点一次。
3. **接管链路彻底不依赖 HlsProxy**。会话表、分片缓存、清单改写全部搬进
   `pngu_hijack`，只用 `pngu_fetch` + `pngu_unwrap` 两个纯函数模块；
   挂载的 ASGI 先问 `pngu_hijack.serve(path)`，未命中才回落 `handle_path`。
   另外 `HlsProxy` 改为按签名过滤参数构造（旧版也能建），且 **18521 监听失败
   不再阻断挂载与接管** —— 独立端口起不来不该把整条播放链路一起废掉。

**0.4.0** —— **接管平台内核的 STRM 播放路由，已有 `.strm` 不用改、不用重扫。**

0.3.x 的死角在这里：`/api/strm/o/<token>.m3u8` 是内核直接发的 302，跳完播放器就
出了 T3FAP，插件无论挂在 18521 还是 8521 都不会被调用。改 `.strm` 内容能解决，
但媒体库几千个文件改起来太贵。

0.4.0 换成「包住那条路由」：插件与平台同进程，把 `app.router.routes` 里那条路由的
`.app`（ASGI 可调用对象）换成包装器。包装器照常调原 `route.app` 拿到 302，再探一下
上游第一片是不是 PNG 壳 —— 是就 200 返回改写后的清单（分片指向
`/api/strm/pngu/seg/<tok>/<n>`），不是就把原 302 字节不动地重放回去。

- 只接管 `/api/strm/` 下 `.m3u8` 结尾的路由，`/api/media/*` 与后台 API 一概不碰
- 只对 3xx 做判断，200/206/404 直接透传，不缓冲不改动
- 探测失败、超时、主清单（多码率）统统放行；结论按上游地址缓存 30 分钟
- **接管装在 `register()` 里，不等 `parse()`** —— 播 STRM 时平台不走解析链，
  `parse()` 永远不会被调用，等它等于没装
- 挂载/接管失败**可重试**（≥15 秒间隔，改配置立刻重试），只有真正装好才封板
- 新增配置 `hijack_strm`（默认开，依赖 `mount_on_platform` 成功）
- 新增诊断：`/api/strm/pngu/__hijack`（接管状态）、`/api/strm/pngu/__probe?url=…`
  （这个源会不会被接管、为什么）
- 卸载时把原 `.app` 装回去

**0.3.1** —— 新增 `tools/rewrite_strm.py`：批量把媒体库里的 `.strm` 改成插件地址，默认预演、自动备份、可一键回滚，保留原文件 BOM 状态。

**0.3.0** —— **把剥壳服务挂到 T3FAP 自己的 8521 端口上**。

平台是 FastAPI，插件与它同进程，`sys.modules` 里就能拿到主应用，于是
`app.mount("/api/strm/pngu", <ASGI>)` 之后：

```
播放器 → http://<NAS>:8521/api/strm/pngu/hls/u/<b64>.m3u8   ← 只碰 8521
       → 插件返回改写后的清单（分片指向 8521 同一前缀）
       → 拉上游 .png 分片，剥掉 61 字节壳，吐 video/mp2t
```

不需要端口映射、不改 compose、其它平台路由不受影响。前缀选 `/api/strm/` 是因为
这个前缀在平台上是**免鉴权**的（`/api/strm/o/<token>` 播放器从不带 token），
放到别处大概率被拦成 401。挂不上（版本差异 / 前缀冲突 / 找不到 app）自动静默
回退到独立端口；`disable` / `uninstall` 原地摘掉路由。

**0.2.3** —— **修真实分片剥不出来**。以前用「剥完长度必须能被 188 整除」判断是不是
TS，icve / douyinbit 系分片末尾有 12 字节残包，永远不整除，于是被判成「不是 TS」原样
透传 —— 播放器拿到 PNG，硬解失败。现在改成按同步率判断（`body[::188]` 里 `0x47` 占比

1.0000，与 fpkvip 的 `_locate_ts` 结果完全一致。
